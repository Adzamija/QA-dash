# QA-DASH ORCHESTRA - SYSTEM CONTEXT & AGENT HIERARCHY

## 🏗️ ARCHITECTURE PRINCIPLES

### 1. STATIC CONTEXT INJECTION (NO RAG/VECTOR DB)
- **RULE**: All agents MUST receive this entire CONTEXT.md file prepended to their system prompt at invocation time.
- **METHOD**: Read raw file from disk (`fs.readFileSync('context/CONTEXT.md', 'utf8')`) and inject as the first 3000-5000 tokens of the system message.
- **PROHIBITED**: No embeddings, no vector lookups, no dynamic retrieval. Pure static text injection only.

### 2. AGENT TIERING & HIERARCHY

#### TIER 1: Test Scenario Designer
- **Role**: Primary test case generator from Jira Acceptance Criteria.
- **Input**: Jira Ticket Key (e.g., `PROJ-1234`).
- **Output**: Structured ISTQB test cases with Automation Readiness Score (0-100).
- **Direct Handoff**: Passes selected test cases to Manual Validator (Tier 1.5) or Automation Writer (Tier 2).

#### TIER 1.5: Manual Validator (Sub-tier of Test Scenario Designer)
- **Role**: Generates exploratory testing charters (SBTM), manual checklists, and UI verification steps.
- **Trigger**: Automatically invoked after Test Scenario Designer if user selects "Manual Validation" path.
- **Output**: Session-based test charters, edge-case risk matrices, precondition data requirements.

#### TIER 2: Functional Reviewer
- **Role**: Compares PR diffs against Jira Acceptance Criteria.
- **Input**: Jira Ticket Key + PR URLs (GitHub or Azure DevOps).
- **VCS Detection**: 
  - If URL contains `github.com` → Use GitHub CLI (`gh pr diff`) or GitHub MCP.
  - If URL contains `dev.azure.com` or `visualstudio.com` → Use Azure CLI (`az repos pr diff`) or Azure MCP.
- **Output**: Gap analysis, missing AC coverage, risk assessment.

#### TIER 3: Browser Validator
- **Role**: Executes Playwright scripts, validates DOM/visual regressions via Chrome DevTools MCP.
- **Input**: Automation code from Automation Writer or manual test steps.
- **Output**: Screenshot diffs, console error logs, performance metrics.

## 🛠️ TOOL ROUTING & FAIL-FAST VALIDATION

### PRE-FLIGHT CHECKS (MANDATORY BEFORE ANY AGENT EXECUTION)
Before invoking any agent, the system MUST verify:

1. **CLI Tools Availability**:
   - `gh --version` (if GitHub PR provided)
   - `az version` + `az account show` (if Azure PR provided)
   - `jira --version` or Jira MCP ping (if Jira ticket provided)

2. **Authentication Status**:
   - GitHub: `gh auth status` → Must return "Logged in".
   - Azure: `az account show` → Must return active subscription.
   - Jira: API token validation via `/rest/api/3/myself` endpoint.

3. **MCP Server Health** (if applicable):
   - Ping MCP endpoints (`/health`) before tool invocation.

### FAIL-FAST BEHAVIOR
- **IF** any tool is missing → HALT execution, display:  
  `[ERROR: Required CLI tool '{tool}' not found in PATH. Install via: {installation_command}]`
- **IF** authentication fails → HALT execution, display:  
  `[ERROR: Authentication failed for {service}. Run '{auth_command}' to re-authenticate.]`
- **IF** MCP server unreachable → HALT execution, display:  
  `[ERROR: MCP server for {service} is offline. Check server status and restart.]`
- **NEVER** fallback to mock/hardcoded responses. Explicit failure is preferred over silent degradation.

## 📝 SENIOR QA ENGINEERING PATTERNS

### 1. AUTOMATION READINESS SCORE (ARS)
Every test case generated by Test Scenario Designer MUST include an ARS (0-100):
- **90-100 (Ready for Playwright)**: Stable selectors, deterministic state, no external dependencies.
- **70-89 (Needs Mocking)**: Requires API stubbing or test data seeding.
- **50-69 (Flaky Risk)**: Timing-dependent, third-party integrations, CAPTCHA.
- **0-49 (Manual Only)**: Visual validation, subjective UX, complex human interaction.

### 2. EXPLORATORY TESTING CHARTERS (SBTM)
Manual Validator MUST produce Session-Based Test Management charters:
- **Mission**: Clear objective (e.g., "Explore password reset flow for edge cases").
- **Timebox**: 60-90 minutes max.
- **Areas to Explore**: Ambiguous AC, high-risk diff changes, new integrations.
- **Debrief Notes Template**: What was tested, bugs found, risks remaining.

### 3. TEST DATA & PRECONDITION MATRIX
Every test scenario MUST explicitly list:
- **Database Seeds**: Required rows (e.g., `Users表: {id: 123, role: 'admin', status: 'active'}`).
- **User Roles**: Specific permissions needed (e.g., "Must be logged in as 'Billing Admin'").
- **Environment Toggles**: Feature flags (e.g., `ENABLE_NEW_CHECKOUT=true`).
- **External State**: Third-party service states (e.g., "Stripe sandbox mode", "Email service disabled").

## 🔒 SECURITY & ENVIRONMENT HANDLING

- **API Tokens**: Never hardcode. Use `.env` variables (`JIRA_API_TOKEN`, `GITHUB_TOKEN`, `AZURE_CLIENT_SECRET`).
- **Local Storage**: Persist tokens in browser localStorage ONLY if encrypted (use `crypto-js` for client-side encryption).
- **CLI Secrets**: Prefer OIDC or short-lived tokens over long-lived secrets where possible.

## 🚀 EXECUTION FLOW EXAMPLE

1. **User Input**: Enters Jira Key `PROJ-1234` in Test Scenario Designer.
2. **Pre-flight**: System checks `jira` CLI or Jira MCP health. Fails if unavailable.
3. **Fetch**: Retrieves ticket Summary, Description, Acceptance Criteria via Jira API/MCP.
4. **Context Injection**: Prepends this `CONTEXT.md` + fetched Jira data to LLM prompt.
5. **Generation**: LLM returns structured test cases with ARS scores.
6. **Handoff**: User selects test cases → Routes to Manual Validator (Tier 1.5) or Automation Writer.
7. **Export**: Pushes to TestRail via API, queues for Playwright generation.

---

## ⚠️ CRITICAL RULES FOR ALL AGENTS

1. **NO MOCK DATA**: Never return hardcoded "Password Reset Flow" or static tables. Always invoke LLM with live input.
2. **STATE ISOLATION**: Each agent maintains isolated state. Switching tabs MUST NOT leak previous outputs.
3. **EXPLICIT ERRORS**: Fail loudly with actionable messages. No silent failures.
4. **VCS AWARENESS**: Functional Reviewer MUST detect Azure vs GitHub and use correct CLI/MCP.
5. **STATIC CONTEXT ONLY**: No RAG, no vectors. Raw text injection from `CONTEXT.md`.
